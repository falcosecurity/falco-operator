# Migration Guide: v0.2.x–v0.4.x and v0.5.0 release candidates to v0.5.0

Version v0.5.0 changes how artifacts reach Falco. The instance operator now fetches every artifact, serves it from a central artifact server, and assigns it to the nodes through one `ArtifactNode` per namespace and node. The `artifact-operator` sidecar in each Falco pod installs what its node's `ArtifactNode` lists and reloads Falco. The release also enables compatibility enforcement by default and changes the managed Falco pod template.

Test the upgrade in a staging environment first. Keep existing custom resources and CRDs: this migration does not require deleting and recreating them. Updating the operator replaces the managed Falco pods, so plan for a workload rollout.

## Find your upgrade path

| Installed version | Chart version | Follow |
|-------------------|---------------|--------|
| v0.1.x | — | The [v0.1.x → v0.2.0](v0.1.x-to-v0.2.0.md) guide first, then every step of this guide. |
| v0.2.x, v0.3.x, v0.4.x | 0.1.0 – 0.3.1 | Every step of this guide. Releases v0.2.x to v0.4.x have no breaking changes between them. |
| v0.5.0-rc1, rc2, rc3 | 0.4.0-rc1, rc2, rc3 | [Upgrading from a release candidate](#upgrading-from-a-release-candidate), then this guide without step 3. |
| v0.5.0-rc4 | none published | [Upgrading from a release candidate](#upgrading-from-a-release-candidate), then steps 1, 4 and 6. |

The chart version and the operator version are not interchangeable: check the `appVersion` of your installed chart (`helm list -n <namespace>`) and the image tag of the operator Deployment to tell which operator you are running.

## What changes in v0.5.0

Each change links to the step that handles it.

| Change | Who must act |
|--------|--------------|
| Artifacts are fetched by the instance operator, not by the Falco pods. Falco pods download them from the operator's artifact Service on TCP 8082. | Anyone restricting network traffic: [step 2](#step-2-check-the-cluster-before-upgrading). |
| The `artifact-operator` sidecar is a regular container, no longer a restartable init container. | Anyone overriding the sidecar in a `Falco` CR: [step 3](#step-3-prepare-artifact-operator-container-overrides). |
| Compatibility enforcement is on by default (`enforceRequirements: true`). v0.4.x installed every artifact regardless of its requirements. | Anyone with rules files or plugins that declare no requirements: [step 2](#step-2-check-the-cluster-before-upgrading). |
| The sidecar waits for Falco's `/versions` API before installing rules files and plugins. | Anyone who disabled or moved the Falco webserver: [step 2](#step-2-check-the-cluster-before-upgrading). |
| The sidecar reloads Falco by sending it SIGHUP. v0.4.x relied on Falco's own file watcher. | Clusters with AppArmor nodes, such as Ubuntu: [step 2](#step-2-check-the-cluster-before-upgrading). |
| The Falco pod shares its process namespace, the sidecar runs as UID 0, and Falco mounts the host's `/sys/kernel` read-only. | Clusters with admission policies on pods: [step 2](#step-2-check-the-cluster-before-upgrading). |
| The default Falco version moves from 0.44.1 to 0.45.2. Component defaults move too: Falcosidekick 2.32.0 to 2.35.1, Falcosidekick UI 2.2.0 to 2.3.1, k8s-metacollector 0.1.2 to 0.1.5. | Anyone not pinning `spec.version`: [step 2](#step-2-check-the-cluster-before-upgrading). |
| `Component` resources must have a `spec`. | Anyone with a `Component` without `spec`: [step 2](#step-2-check-the-cluster-before-upgrading). |
| New `ArtifactNode` CRD and new status fields on `Rulesfile`, `Plugin` and `Config`. | Everyone: [step 4](#step-4-update-crds-and-the-operator). |
| New permissions: `ArtifactNode` access, Leases for leader election, and cert-manager Certificates when mTLS is enabled. Falco pods no longer read Secrets. | Anyone managing RBAC outside the chart: [step 4](#step-4-update-crds-and-the-operator). |
| The sidecar image follows the instance operator release; `imageRegistry` selects a mirror. | Anyone pinning operator images or using a mirror: [step 3](#step-3-prepare-artifact-operator-container-overrides). |
| The chart's default operator memory is raised to 128Mi requests and 512Mi limits. | Namespaces with tight resource quotas. |

## Upgrading from a release candidate

The release candidates already run the sidecar as a regular container, so their `Falco` CRs need no change for it. Check two things before following the steps for your version in the [table above](#find-your-upgrade-path):

- **Remove the `--artifact-operator-image` argument and the `ARTIFACT_OPERATOR_IMAGE` environment variable** from the instance operator, for example from the Helm values `extraArgs` and `extraEnv`. rc1 to rc3 accepted them; v0.5.0 does not know the flag and exits at startup with `flag provided but not defined: -artifact-operator-image`, leaving the upgrade stuck with the old pod still running. Use `imageRegistry` to select a mirror instead, see [step 3](#step-3-prepare-artifact-operator-container-overrides).
- **Do not delete `ArtifactNode` objects by hand**, neither before nor after the upgrade. rc1 to rc3 created one `ArtifactNode` per artifact and node; v0.5.0 creates one per namespace and node, named after the node. The new operator deletes the old objects on its own and releases their finalizers. Deleting them while an rc1 to rc3 operator still runs does not help: that operator recreates them at once, and its sidecars remove and reinstall the files in the meantime, which reloads Falco repeatedly and leaves it briefly without the rules.

rc4 already uses one `ArtifactNode` per node: the upgrade keeps those objects as they are.

## Step 1: Back up existing resources

Save the current CRDs and custom resources, including their UIDs, before changing the installation. Run these steps in the same Bash session and stop if a command fails:

```bash
set -o pipefail
MIGRATION_DIR="$(mktemp -d)"
MIGRATION_RESOURCES="falcos.instance.falcosecurity.dev,components.instance.falcosecurity.dev,rulesfiles.artifact.falcosecurity.dev,plugins.artifact.falcosecurity.dev,configs.artifact.falcosecurity.dev"

kubectl get crd \
  falcos.instance.falcosecurity.dev components.instance.falcosecurity.dev \
  rulesfiles.artifact.falcosecurity.dev plugins.artifact.falcosecurity.dev \
  configs.artifact.falcosecurity.dev -o yaml > "$MIGRATION_DIR/crds-before.yaml"

kubectl get "$MIGRATION_RESOURCES" --all-namespaces -o yaml > "$MIGRATION_DIR/resources-before.yaml"
kubectl get "$MIGRATION_RESOURCES" --all-namespaces \
  -o custom-columns=KIND:.kind,NAMESPACE:.metadata.namespace,NAME:.metadata.name,UID:.metadata.uid \
  --no-headers | sort > "$MIGRATION_DIR/uids-before.txt"
```

Keep your Helm values or installer customizations alongside these backups. These commands do not export Kubernetes Secrets, but custom resources and values can contain sensitive configuration; keep the backup directory private.

## Step 2: Check the cluster before upgrading

### Artifact compatibility

With the default `enforceRequirements: true`, an OCI plugin with no declared requirements, or a Rulesfile with neither requirements nor plugin dependencies, is blocked: it is not installed, and it reports `Programmed=False` with `DependenciesSatisfied=Unknown`. The check covers every Rulesfile source, including inline rules and rules from ConfigMaps. The upgrade replaces every Falco pod, and replacement pods start with empty artifact volumes, so an artifact that v0.4.x installed but v0.5.0 blocks is missing from Falco after the upgrade. Review Plugin OCI metadata and every Rulesfile source, add the actual `required_engine_version` and `required_plugin_versions` declarations where needed, and verify them against the target Falco version. See [artifact compatibility](../configuration.md#artifact-compatibility).

If metadata cannot yet be supplied, explicitly choose `enforceRequirements: false` in the reviewed Helm values (or `--enforce-requirements=false` for a non-Helm instance operator). Advise mode permits installation but does not make artifacts compatible. An update rejected on an existing pod can retain its old files; replacement pods have empty volumes and cannot retain that previous installation.

### Falco version

A `Falco` resource that does not pin a version moves from Falco 0.44.1 to 0.45.2 with this upgrade. Review the Falco 0.45 release notes against your configuration and rules, or set `spec.version` to keep the version you run today and upgrade Falco separately. See the [version matrix](../version-matrix.md).

### Falco API

The sidecar waits for Falco's `/versions` API before installing rules files and plugins, even in advise mode; Config resources are delivered without this wait. Keep the Falco webserver accessible at its default `http://localhost:8765`, or configure the sidecar's `FALCO_URL` and Falco probes for your endpoint. Optional metrics are separate from this [API prerequisite](../configuration.md#falco-api-prerequisite).

### AppArmor nodes

The sidecar now reloads Falco with SIGHUP. On nodes where the container runtime applies its default AppArmor profile, such as Ubuntu with containerd, the signal is denied: the sidecar logs `failed to send SIGHUP to Falco; will retry` with `permission denied`, and the pods look healthy while Falco may not apply new or changed artifacts. If you have such nodes, set `artifactOperatorAppArmorUnconfined: true` in your Helm values (or `--artifact-operator-apparmor-unconfined` for a non-Helm instance operator); it requires Kubernetes 1.30 or later. See [reloads on AppArmor nodes](../configuration.md#reloads-on-apparmor-nodes).

### Admission policies

The managed Falco pod now sets `shareProcessNamespace: true`, runs the `artifact-operator` container as UID 0, and mounts the host path `/sys/kernel` read-only into the Falco container. If Pod Security admission, Kyverno, Gatekeeper or similar policies apply to Falco namespaces, check that they admit these settings, or the replacement pods are not created.

### Components without spec

A `Component` must now have a `spec`. List those that have none and add one, or delete them, before upgrading:

```bash
kubectl get components.instance.falcosecurity.dev --all-namespaces -o json |
  jq -r '.items[] | select(.spec == null) | "\(.metadata.namespace)/\(.metadata.name)"'
```

### Network access

Allow Falco pods to reach the artifact Service on TCP 8082, and the instance operator to reach the registries of your OCI artifacts; keep Kubernetes API and DNS access available. Pull secrets referenced by artifacts are now read by the instance operator rather than by the Falco pods.

mTLS is optional and can be enabled in the same upgrade by setting `mtls.enabled: true`; the chart then creates the CA, issuers and certificates as part of `helm upgrade`. Before upgrading, complete [PKI and trust-bundle onboarding](../installation.md#artifact-transport-and-mtls), including the trust label on the operator namespace **and every Falco namespace**. A Falco namespace without the label never receives the CA bundle ConfigMap: its replacement pods stay in `ContainerCreating` with `configmap "falco-operator-artifact-ca-bundle" not found`, and since the DaemonSet has already removed the old pod, that node runs without Falco until you label the namespace. Labeling it later lets the rollout continue without further action.

## Step 3: Prepare Artifact Operator container overrides

Skip this step when upgrading from a release candidate.

The `artifact-operator` sidecar is now a regular container instead of a restartable init container. If your `Falco` CR customizes this container, prepare an updated manifest:

1. Move the entry named `artifact-operator` from `spec.podTemplateSpec.spec.initContainers` to `spec.podTemplateSpec.spec.containers`, preserving its overrides.
2. Remove its `restartPolicy: Always` if present; this field belonged to the restartable init container.
3. Keep unrelated init containers unchanged.
4. If the override pins an Artifact Operator image, update it to the version matching the new instance operator. Also review any operator image pins in your Helm values.

For example, this v0.4.x override:

```yaml
spec:
  podTemplateSpec:
    spec:
      initContainers:
        - name: artifact-operator
          resources:
            requests:
              memory: 64Mi
```

becomes:

```yaml
spec:
  podTemplateSpec:
    spec:
      containers:
        - name: artifact-operator
          resources:
            requests:
              memory: 64Mi
```

Apply the revised manifests in [step 5](#step-5-apply-the-prepared-falco-manifests), after updating the instance operator. Until then, the new operator reports `Reconciled=False` with `sidecar "artifact-operator" must be configured in spec.podTemplateSpec.spec.containers, not initContainers` on that `Falco` CR and leaves its existing workload untouched, so its pods keep running with the files they already have. If you do not override the `artifact-operator` container, no change to the `Falco` CR is needed.

The sidecar tag is embedded in the selected instance operator release, so the two operators remain paired without a runtime tag setting. Use `imageRegistry` in Helm values to pull every default image from a mirror. Custom repositories and digest pins belong in the Falco container override above.

## Step 4: Update CRDs and the operator

### Helm

Helm does not upgrade CRDs from a chart's `crds/` directory, so apply them first. Choose the target **chart** version and check that its `appVersion` is the operator version you want:

```bash
CHART_VERSION="<target-chart-version>"
CRD_FILE="$(mktemp)"
helm repo update
helm show chart falcosecurity/falco-operator --version "$CHART_VERSION"
helm show crds falcosecurity/falco-operator --version "$CHART_VERSION" > "$CRD_FILE"
```

Apply the CRDs with server-side apply and wait until every CRD in the file is established:

```bash
kubectl apply --server-side --force-conflicts -f "$CRD_FILE" &&
kubectl wait --for=condition=Established --timeout=120s -f "$CRD_FILE"
```

`--force-conflicts` is required for CRDs that Helm installed: Helm recorded itself as their field manager, and without the flag the apply stops with `conflict with "helm": .spec.versions`. Taking ownership is safe here because Helm never updates or removes CRDs from `crds/` afterwards. If the conflict names another manager, such as a GitOps controller, update the CRDs through that tool instead. Do not delete CRDs to resolve a conflict, because that also deletes their custom resources.

Once the CRDs are established, upgrade the release with your reviewed values file:

```bash
helm upgrade falco-operator falcosecurity/falco-operator \
  --namespace falco-operator \
  --version "$CHART_VERSION" \
  --values my-values.yaml \
  --wait --timeout 5m
```

Updating only the operator image, or running `helm upgrade` without the CRD step, is insufficient. The old installation has no `ArtifactNode` CRD and lacks the status fields used by the new controllers. Upgrade the complete chart, including its RBAC and artifact server Service.

If `rbac.create: false`, update your managed roles too: artifact delivery requires `ArtifactNode` access, leader election requires Leases, and optional mTLS requires Certificate access. Compare the target release's [permission inventory](../installation.md#required-permissions), not only its Deployment.

### YAML manifest

Apply the target operator release's complete `install.yaml` using the [YAML upgrade procedure](../installation.md#upgrade-1). That installer includes the CRDs and operator resources; do not replace only the Deployment image. Use an explicit release version rather than `latest` for a repeatable migration.

### During the rollout

The operator then replaces the Falco pods according to each workload's update strategy. Until a node's old pod is gone, the old sidecar keeps adding its per-node finalizers to `Rulesfile`, `Plugin` and `Config` objects and the new operator removes them; the operator may log `the object has been modified` conflicts while this happens. They stop once the rollout completes. Do not remove finalizers manually as part of this procedure.

## Step 5: Apply the prepared Falco manifests

Apply the `Falco` manifests prepared in [step 3](#step-3-prepare-artifact-operator-container-overrides), if any, and wait for their rollout. Their `Reconciled` condition must become `True`.

## Step 6: Verify the migrated workloads and artifacts

Helm's `--wait` does not establish that every Falco workload and artifact has converged. Check the managed DaemonSet or Deployment rollout in each Falco namespace, including any rollout strategy you customized.

Without creating or deleting custom resources during this comparison, verify that the original parent resources kept their UIDs:

```bash
kubectl get "$MIGRATION_RESOURCES" --all-namespaces \
  -o custom-columns=KIND:.kind,NAMESPACE:.metadata.namespace,NAME:.metadata.name,UID:.metadata.uid \
  --no-headers | sort > "$MIGRATION_DIR/uids-after.txt"
diff -u "$MIGRATION_DIR/uids-before.txt" "$MIGRATION_DIR/uids-after.txt"

kubectl get artifactnodes.artifact.falcosecurity.dev --all-namespaces
kubectl get rulesfiles.artifact.falcosecurity.dev,plugins.artifact.falcosecurity.dev,configs.artifact.falcosecurity.dev --all-namespaces
```

Each Falco namespace has one `ArtifactNode` per node running a Falco pod, named after the node. For each intended artifact assignment, inspect the parent and the `ArtifactNode` of each node it should reach: the node's `spec.artifacts` must list the artifact, and its entry in `status.artifacts` must report successful programming. Check that the parent's `status.observedGeneration` matches its current generation; investigate pending or failed conditions instead of treating an operator Ready pod as proof of success. A parent's `Programmed` condition can still date from before the upgrade, so check the `ArtifactNode` entries too.

Inspect `DependenciesSatisfied` for compatibility blocks and update-rejected reasons. Also check each condition's `observedGeneration`: an older source condition may describe retained files, not successful installation of the update.

Verify the expected files inside the Falco container (`/etc/falco/rules.d`, `/etc/falco/config.d`, `/usr/share/falco/plugins`) and that Falco loads the intended rules and plugins; its log shows `SIGHUP received, restarting...` followed by the loaded files after each delivery. In staging, also update and remove an artifact after upgrading to confirm that reconciliation, reloads and cleanup still work.
