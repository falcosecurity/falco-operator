# Migration Guide: v0.4.x to v0.5.0

Version v0.5.0 adds the `ArtifactNode` CRD, new artifact status fields, and a central artifact server. It also changes where the Artifact Operator container runs in each Falco pod.

Test the upgrade in a staging environment first. Keep existing custom resources and CRDs: this migration does not require deleting and recreating them. Updating the operator also changes the managed Falco pod templates, so plan for a workload rollout.

## Step 1: Back up existing resources

Save the current CRDs and custom resources, including their UIDs, before changing the installation. Run these steps in the same Bash session and stop if a command fails:

```bash
set -o pipefail
MIGRATION_DIR="$(mktemp -d)"
MIGRATION_RESOURCES="falcos.instance.falcosecurity.dev,components.instance.falcosecurity.dev,rulesfiles.artifact.falcosecurity.dev,plugins.artifact.falcosecurity.dev,configs.artifact.falcosecurity.dev"

kubectl get crd \
  falcos.instance.falcosecurity.dev components.instance.falcosecurity.dev \
  rulesfiles.artifact.falcosecurity.dev plugins.artifact.falcosecurity.dev \
  configs.artifact.falcosecurity.dev -o yaml > "$MIGRATION_DIR/crds-before.yaml"

kubectl get "$MIGRATION_RESOURCES" --all-namespaces -o yaml > "$MIGRATION_DIR/resources-before.yaml"
kubectl get "$MIGRATION_RESOURCES" --all-namespaces \
  -o custom-columns=KIND:.kind,NAMESPACE:.metadata.namespace,NAME:.metadata.name,UID:.metadata.uid \
  --no-headers | sort > "$MIGRATION_DIR/uids-before.txt"
```

Keep your Helm values or installer customizations alongside these backups. These commands do not export Kubernetes Secrets, but custom resources and values can contain sensitive configuration; keep the backup directory private.

## Step 2: Prepare Artifact Operator container overrides

The `artifact-operator` sidecar is now a regular container instead of a restartable init container.

If your `Falco` CR customizes this container, prepare an updated manifest:

1. Move the entry named `artifact-operator` from `spec.podTemplateSpec.spec.initContainers` to `spec.podTemplateSpec.spec.containers`, preserving its overrides.
2. Remove its `restartPolicy: Always` if present; this field belonged to the restartable init container.
3. Keep unrelated init containers unchanged.
4. If the override pins an Artifact Operator image, update it to the version matching the new instance operator. Also review any operator image pins in your Helm values.

Apply the revised Falco manifests after updating the instance operator in the next step. The new operator reports misplaced overrides instead of converting them automatically. If you do not override the `artifact-operator` container, no manual change to the `Falco` CR is needed for this container migration.

## Step 3: Update CRDs and the operator

For Helm installations, follow the [Helm upgrade procedure](../installation.md#upgrade): use `helm show crds --version` for the target **chart** version, apply that file with server-side apply, and wait for every CRD in it to be established before running `helm upgrade` with your reviewed values file. The chart version and operator version are not interchangeable.

Updating only the operator image or running `helm upgrade` without the CRD step is insufficient. The old installation has no `ArtifactNode` CRD and lacks the status fields used by the new controllers. Upgrade the complete chart, including its RBAC and artifact server Service.

For YAML installations, apply the target operator release's complete `install.yaml` using the [YAML upgrade procedure](../installation.md#upgrade-1). That installer includes the CRDs and operator resources; do not replace only the Deployment image. Use an explicit release version rather than `latest` for a repeatable migration.

After the instance operator is running, apply any Falco manifests prepared in step 2. The operator handles its legacy per-node artifact finalizers; do not remove finalizers manually as part of this procedure.

## Step 4: Verify the migrated workloads and artifacts

Helm's `--wait` does not establish that every Falco workload and artifact has converged. Check the managed DaemonSet or Deployment rollout in each Falco namespace, including any rollout strategy you customized.

Without creating or deleting custom resources during this comparison, verify that the original parent resources kept their UIDs:

```bash
kubectl get "$MIGRATION_RESOURCES" --all-namespaces \
  -o custom-columns=KIND:.kind,NAMESPACE:.metadata.namespace,NAME:.metadata.name,UID:.metadata.uid \
  --no-headers | sort > "$MIGRATION_DIR/uids-after.txt"
diff -u "$MIGRATION_DIR/uids-before.txt" "$MIGRATION_DIR/uids-after.txt"

kubectl get artifactnodes.artifact.falcosecurity.dev --all-namespaces
kubectl get rulesfiles.artifact.falcosecurity.dev,plugins.artifact.falcosecurity.dev,configs.artifact.falcosecurity.dev --all-namespaces
```

For each intended artifact assignment, inspect the parent and its `ArtifactNode`: the node must match the Falco workload, and the conditions must report successful programming. Check that the parent's `status.observedGeneration` matches its current generation; investigate pending or failed conditions instead of treating an operator Ready pod as proof of success.

Verify the expected files inside the Falco container (`/etc/falco/rules.d`, `/etc/falco/config.d`, `/usr/share/falco/plugins`) and that Falco loads the intended rules and plugins. In staging, also update and remove an artifact after upgrading to confirm that reconciliation and cleanup still work.
